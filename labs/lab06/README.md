- [x] 5. Проведите анализ уязвимостей, опишите их причину возникновения

 1. Уязвимости уровня хоста (Host Configuration)

  Отсутствие отдельного раздела для контейнеров (1.1)
**Причина:** `/var/lib/docker` расположен в общей файловой системе хоста.  
**Влияние:** при переполнении диска контейнером возможен отказ в обслуживании всей ОС.  
**Сценарий атаки:** злоумышленник внутри контейнера генерирует большой объём данных → заполняется диск → хост недоступен (DoS).

Не настроен аудит Docker
**Причина:** отсутствуют auditd-правила для Docker daemon, сокета и конфигурационных файлов.  
**Влияние:** невозможность обнаружения атак и несанкционированных действий.  
**Сценарий атаки:** злоумышленник меняет конфигурацию Docker или запускает контейнеры с повышенными привилегиями без следов в журналах.

---

2. Конфигурация Docker daemon

Отсутствует изоляция контейнеров в bridge-сети (2.1)
**Причина:** межконтейнерный трафик не ограничен.  
**Влияние:** контейнеры могут перехватывать или подменять трафик друг друга.  
**Сценарий атаки:** lateral movement между контейнерами, sniffing сетевого трафика.

Не включены user namespaces (2.8)
**Причина:** контейнерный root сопоставляется с root хоста.  
**Влияние:** при escape-уязвимости контейнера атакующий получает root на хосте.  
**Сценарий атаки:** exploit ядра Linux → полный захват хоста.

Отсутствует авторизация Docker API (2.11)
**Причина:** не используется authz-плагин.  
**Влияние:** любой пользователь с доступом к Docker может управлять всей инфраструктурой.  
**Сценарий атаки:** запуск привилегированного контейнера → захват системы.

Отключён запрет получения новых привилегий (2.18)
**Причина:** `no-new-privileges` не установлен.  
**Влияние:** возможна эскалация привилегий внутри контейнера.  
**Сценарий атаки:** exploit SUID-бинарей внутри контейнера.

---

3. Образы контейнеров

Контейнеры запускаются от root (4.1)
**Причина:** отсутствует директива `USER` в Dockerfile.  
**Влияние:** повышенные привилегии внутри контейнера.  
**Сценарий атаки:** RCE в веб-приложении → root-доступ внутри контейнера → escape.

Отсутствуют HEALTHCHECK (4.6)
**Причина:** образы не содержат инструкцию HEALTHCHECK.  
**Влияние:** невозможность обнаружения зависших или скомпрометированных контейнеров.  
**Сценарий атаки:** вредоносный код продолжает работу без перезапуска контейнера.

Не используется Docker Content Trust (4.5)
**Причина:** образы не подписаны и не проверяются.  
**Влияние:** риск использования подменённых образов.  
**Сценарий атаки:** supply-chain атака через публичный registry.

---

4. Runtime-уязвимости контейнеров (критично)

Привилегированный контейнер `vulnerable-web` (5.4)
**Причина:** используется `privileged: true`.  
**Влияние:** контейнер получает почти полный доступ к хосту.  
**Сценарий атаки:** attacker → контейнер → доступ к `/dev`, ядру, хостовой ОС → полный compromise.

Добавлены все Linux capabilities (5.3)
**Причина:** `CapAdd=[ALL]`.  
**Влияние:** обход системных ограничений ядра.  
**Сценарий атаки:** загрузка модулей ядра, управление сетевыми интерфейсами.

Используется `network_mode: host` (5.9)
**Причина:** контейнер разделяет сетевой стек хоста.  
**Влияние:** доступ ко всем сервисам хоста, bypass firewall.  
**Сценарий атаки:** сканирование localhost, атака на сервисы хоста.

Общий PID namespace с хостом (5.15)
**Причина:** `pid: host`.  
**Влияние:** контейнер видит процессы хоста.  
**Сценарий атаки:** завершение процессов, ptrace-атаки.

Docker socket смонтирован в контейнер (5.31)
**Причина:** `/var/run/docker.sock` доступен внутри контейнера.  
**Влияние:** полный контроль над Docker daemon.  
**Сценарий атаки:** запуск нового привилегированного контейнера → root на хосте.

Нет лимитов ресурсов (5.10, 5.11, 5.28)
**Причина:** отсутствуют memory / cpu / pids ограничения.  
**Влияние:** DoS хоста.  
**Сценарий атаки:** fork bomb или memory exhaustion.

Root FS доступна на запись (5.12)
**Причина:** `read_only` не задан.  
**Влияние:** сохранение вредоносных файлов внутри контейнера.  
**Сценарий атаки:** persistence malware.

Отключён seccomp профиль (5.21)
**Причина:** seccomp disabled.  
**Влияние:** системные вызовы не фильтруются.  
**Сценарий атаки:** использование опасных syscall для escape.

5. Docker Swarm (если не используется)

Включён Swarm без необходимости (7.1)
**Причина:** swarm mode активен.  
**Влияние:** расширение поверхности атаки.  
**Сценарий атаки:** компрометация manager-ноды.

Overlay-сеть без шифрования (7.4)
**Причина:** трафик ingress не зашифрован.  
**Влияние:** перехват данных между узлами.  
**Сценарий атаки:** MITM между swarm-нодами.

#### Захват контроля над хостом через docker.sock

При получении удалённого выполнения команд внутри контейнера `vulnerable-web` (например, из‑за ошибок конфигурации или уязвимостей веб‑приложения) наличие сокета `/var/run/docker.sock` даёт атакующему возможность напрямую управлять Docker на хостовой системе. Через Docker API можно запускать дополнительные контейнеры с монтированием корневой файловой системы и расширенными правами, читать системные файлы, изменять конфигурации и внедрять постоянный доступ. В результате хост полностью теряет контроль.

#### Выход за пределы контейнера

Использование режима `privileged`, добавление всех capabilities и отключение механизмов seccomp и AppArmor фактически убирают изоляцию контейнера. В таком окружении злоумышленник может применять опасные системные вызовы или эксплуатировать уязвимости ядра, что приводит к выполнению действий на уровне хоста и полной компрометации системы.

#### Отказ в обслуживании за счёт исчерпания ресурсов

При отсутствии лимитов на использование CPU, памяти и количества процессов контейнер способен занять все доступные ресурсы. Это может привести к деградации сервисов или полной недоступности системы для легитимных пользователей.

 Риски в docker-compose.yml

1. **Сервис базы данных (PostgreSQL)**

   - Пароль администратора задан в явном виде и является тривиальным.
   - Публикация порта базы данных увеличивает площадь атаки.
   - Используются слабые и предсказуемые учётные данные.

   **Оценка рисков:**

   ```text
   DL: высокий — возможна утечка данных при компрометации учётных данных.
   CR: средний — БД может быть использована как точка входа для дальнейших атак.
   ```

2. **Сервис приложения**

   - Секретные ключи и строка подключения к БД хранятся прямо в compose‑файле.
   - Контейнер имеет доступ на запись к исходному коду приложения на хосте.

   **Оценка рисков:**

   ```text
   DL: высокий — утечка секретов и служебной информации.
   CR: средний/высокий — при эксплуатации уязвимости возможна эскалация атаки.
   ```

---

Риски в vulnerable-app.yml

1. **vulnerable-web**

   - Контейнер запущен с максимальными привилегиями.
   - Используются host‑namespace для сети и процессов.
   - Полностью отключены защитные профили безопасности.
   - Смонтированы корневая файловая система хоста и docker.sock.
   - Секреты хранятся в переменных окружения.
   - Образ используется без фиксации версии.

   **Оценка рисков:**

   ```text
   CR: крайне высокий — компрометация контейнера почти гарантированно ведёт к захвату хоста.
   DL: крайне высокий — полный доступ к данным хоста и секретам.
   ```

2. **debug-shell**

   - Контейнер работает от root с привилегиями хоста.
   - Открыт SSH доступ по паролю.
   - Смонтирован корень файловой системы хоста.

   **Оценка рисков:**

   ```text
   CR: крайне высокий — контейнер фактически выполняет роль постоянного backdoor.
   DL: крайне высокий — полный доступ к данным хостовой системы.
   ```

### Рекомендации по снижению рисков

```text
1. Хранить секреты вне compose‑файлов (например, в .env или менеджерах секретов).
2. Исключить использование privileged и cap_add: ALL, применять принцип минимальных привилегий.
3. Запускать контейнеры от непривилегированных пользователей.
4. Не монтировать корневую файловую систему и системные каталоги хоста.
5. Не предоставлять контейнерам доступ к docker.sock.
6. Устанавливать ограничения на использование ресурсов.
7. Использовать read‑only файловые системы и tmpfs для временных каталогов.
8. Отказаться от host‑namespace для сети и PID.
9. Фиксировать версии используемых образов.
```
